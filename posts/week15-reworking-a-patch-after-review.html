Transforming a small patch, into a giant patch

Introduction

Last week we sent our first contribution to Plasma Desktop, !3896 - Group mice by group ID in the device list, which used libinput's device group id to stop the same physical mouse from showing up several times in the Mouse KCM. This week the review came back, and it turned out our approach was wrong in a way we could never have noticed on our own hardware.

The review

The reviewer tested the patch with two Razer mice, and each one exposes three logical devices to the system. The first mouse listed them in this order.

  • Razer ProClickM, which supports left handed mode, pointer acceleration, scrolling speed, invert scroll direction and everything else you would expect.
  • Razer ProClickM Keyboard, which only supports invert scrolling speed and scroll direction.
  • Razer ProClickM Mouse, which claims to support the same things as the first one, except that changing those settings does nothing.

On that mouse our patch worked. We kept the first device of the group, which happened to be the real one, and dropped the other two. The second mouse is where it fell apart, because it lists its devices in a different order.

  • Razer Orochi V2 Mouse, which claims to support everything, except that the settings do nothing.
  • Razer Orochi V2 Keyboard, which only supports invert scrolling speed and scroll direction.
  • Razer Orochi V2, which supports everything and is the one where the settings actually make a difference.

Our code kept the first device it saw and threw the rest away, so the KCM ended up showing "Razer Orochi V2 Mouse" and silently discarding the only device that works. That is worse than the bug we set out to fix. Before the patch the user saw three confusing entries but at least one of them worked. After the patch the user saw a single clean entry that does absolutely nothing.

Two ways forward were suggested. Either be really sure a device is useless before skipping it, or stop skipping devices at all and merge the whole group into a single entry.

The first option needs information we do not have. We could ask KWin which device was used last, but a device that has been quiet so far can still wake up later, so that would only be a guess with extra steps. We went with the second option.

Jakob mentioned two solutions and agreed that the second one was the best. The funny part is that the second solution was actually our first idea, we just discarded it because it looked too complicated.

How we started

The new plan is easy to describe. Stop picking a winner, and treat every device of the same mouse as one thing. The entry shows everything the group can do together, and anything the user changes gets sent to all of them, so it does not matter which one is the real device.

Getting there took three steps. First we deleted the old logic, then we configured a device object to hold several devices at once, and finally we made the list show one entry per group.

mergedProperties is where the review actually gets answered, and it does two passes.

The first pass picks a base device, the one whose properties will provide the current values such as acceleration speed and the device name. It counts how many support flags each device has enabled and keeps the richest one. When two devices tie, it prefers the one with the shorter name. That tiebreak sounds arbitrary but it is exactly what saves the reviewer's second mouse, because "Razer Orochi V2" and "Razer Orochi V2 Mouse" advertise the same capabilities and the shorter name is the real device. The same rule leaves "Razer ProClickM" in place on the first mouse, so both cases land on the right base regardless of the order they arrive in.

The second pass then walks every device again and ORs all the support flags together, so the merged device advertises the union of everything the group can do. This is why an integer OR is used rather than a boolean one, since some of those properties are button masks and not simple true or false values.

Calling init() again after adding a member is the part that makes the ordering problem disappear. Every time a new device joins the group, the merge runs again over all members, so the base device and the union of capabilities are recomputed from scratch. It no longer matters whether the useful device shows up first, second or last, because by the time the list is complete the merge has seen all of them. And finally, we could hide the ugly repeated devices into a single entry, but without forgeting about the other entries.

The Kensington case

While going through the new logic we did find one case where it misbehaves, and it is worth noting, not because it is impactful, but because it is funny.

Some Kensington mice expose a touchpad style device alongside the mouse in the same group. The problem is that a touchpad supports far more settings than a mouse does, things like tap to click, disable while typing and several different scroll methods, so when our first pass counts how many capabilities each device advertises, the touchpad ends up being the representative of the group. The merged entry would then take its name and its current values from the touchpad, but it's just a visual thing, the mouse properties will still be present in the group (but some of then do not actually make sense with a normal mice)

The reason this never actually happens is that KWin does not hand touchpads over to the Mouse KCM in the first place, they belong to the Touchpad KCM instead. The touchpad never enters the group we build, so it can never be picked as the base device. The bug is real in the sense that the code would do the wrong thing, and harmless in the sense that the data needed to trigger it never arrives.
