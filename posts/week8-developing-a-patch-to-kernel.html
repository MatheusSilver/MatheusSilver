Developing a patch to the Linux Kernel

Introduction

In the previous week, we decided to work with the tsl2591 driver, which supports a physical luminosity sensor commonly used in Raspberry Pi projects. In the Linux Kernel context, this driver is responsible for retrieving luminosity data from the sensor and exposing it to the operating system.

Issues with this driver

The issue was first identified by the ArKanjo tool, which is used to detect code duplication in the Linux Kernel and was developed by IME-USP.

The issue pointed out by ArKanjo was related to the following three parts of the tsl2591.c file:

  • 17 macros that define persist registers
  • tsl2591_persist_cycle_to_lit()
  • tsl2591_persist_lit_to_cycle()

Together, these two functions had a total of 37 duplicated lines.

Based on these results, one of the main issues my classmate and I identified was that if someone wanted to implement a new kind of register, the developer would need to update three different parts of the code: the macro, the direct conversion function, and the inverse conversion function. There was also a third different function that we did not address, since it was outside the scope of the issue pointed out by ArKanjo and probably followed a different pattern that we still did not understand.

For completeness, this third function is named tsl2591_compatible_als_persist_cycle(), and it is responsible for checking whether the requested register is available. It also follows the same pattern as the previous two functions, with a large switch-case for each register. However, in this case, it returns a different value.

The whole code that we needed to refactor is given below:

Solution strategy

The first thing we noticed is that not every register definition was used in the conversion. However, the ones that were used followed a value-mapping pattern. So, our first attempt was to create two arrays: one mapping cycle to lit, and another mapping lit to cycle. Even though this strategy solved the duplication, it introduced another problem. If a new register had to be added, another developer would need to understand and preserve the original array ordering, which would make future refactoring harder.

After discussing this with Guilherme Ivo (thanks, Ivo :D), we decided to implement something like a double-entry dictionary that would let us get the key from a value and the value from a key.

However, this decision led to another challenge: "How could we implement this kind of double-entry dictionary without relying on complicated data structures?" The answer was simple and had already been used elsewhere in tsl2591.c.

We decided to use a struct to store both kinds of data, this structure is shown below:

struct tsl2591_persist_entry {
       u8 cycle;
       int lit;
};

By using this structure, the two arrays previously needed for conversion were merged into a single list of structs, which we wrote according to kernel style, as shown below:

static const struct tsl2591_persist_entry tsl2591_persist_table[] = {
       { TSL2591_PRST_ALS_INT_CYCLE_ANY,  1  },
       { TSL2591_PRST_ALS_INT_CYCLE_2,    2  },
       { TSL2591_PRST_ALS_INT_CYCLE_3,    3  },
       { TSL2591_PRST_ALS_INT_CYCLE_5,    5  },
       { TSL2591_PRST_ALS_INT_CYCLE_10,   10 },
       { TSL2591_PRST_ALS_INT_CYCLE_15,   15 },
       { TSL2591_PRST_ALS_INT_CYCLE_20,   20 },
       { TSL2591_PRST_ALS_INT_CYCLE_25,   25 },
       { TSL2591_PRST_ALS_INT_CYCLE_30,   30 },
       { TSL2591_PRST_ALS_INT_CYCLE_35,   35 },
       { TSL2591_PRST_ALS_INT_CYCLE_40,   40 },
       { TSL2591_PRST_ALS_INT_CYCLE_45,   45 },
       { TSL2591_PRST_ALS_INT_CYCLE_50,   50 },
       { TSL2591_PRST_ALS_INT_CYCLE_55,   55 },
       { TSL2591_PRST_ALS_INT_CYCLE_60,   60 },
};

By making these changes, we simplified the process of implementing new registers. A developer now only needs to add a new entry to the table, and both conversion functions automatically support the new register because they read from the same data source. The new versions of tsl2591_persist_cycle_to_lit() and tsl2591_persist_lit_to_cycle() are shown below: 

static int tsl2591_persist_cycle_to_lit(const u8 als_persist)
{
	for (int i = 0; i < ARRAY_SIZE(tsl2591_persist_table); i++) {
		if (als_persist == tsl2591_persist_table[i].cycle)
            return tsl2591_persist_table[i].lit;
	}
	return -EINVAL;
}

static int tsl2591_persist_lit_to_cycle(const u8 als_persist)
{
	for (int i = 0; i < ARRAY_SIZE(tsl2591_persist_table); i++) {
        if (als_persist == tsl2591_persist_table[i].lit)
			return tsl2591_persist_table[i].cycle;
	}
	return -EINVAL;
}

This is how we attempted to solve the code duplication issue. We are currently awaiting the maintainer's feedback to confirm whether the implementation is correct.

Experience

To be honest, resolving the issue itself was not the hardest part of the process. The hardest part was deciding how to style our code to stay aligned with the original kernel standards. That is why one of our thanks goes to Guilherme Ivo, who pointed out style issues, including some related to struct formatting and others related to array construction, such as keeping a trailing comma in the last array entry to simplify future maintenance. We honestly did not know that we could keep a trailing comma on the last array element without causing compile errors.
